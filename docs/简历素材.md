## 一、项目一句话定位

> 基于「编译式知识库」的企业培训智能问答助手：把散落在聊天记录、会议纪要、培训手册、界面截图里的业务知识，清洗脱敏后**编译成可溯源、可互链的结构化 Wiki**（819 页），通过飞书机器人提供「一句话检索 + 引用溯源」的问答服务。

**技术栈标签**：LLM Wiki（Karpathy 编译式方法论）｜ 智谱 GLM（国产大模型）｜ 混合检索（关键词 + 图谱；向量已接入但因额度未生效）｜ 飞书长连接机器人 ｜ 多模态（GLM-4V 截图 OCR）

**简历时间写法建议**：`2026.09–至今（语料为实习期积累的 173 份真实业务文档）`
——单写 `2026.09` 会引发"一个月就做完？"的质疑，见 §五 Q8。

## 二、核心 bullet（STAR 结构，挑 3~4 条）

### 1. 数据工程（最硬核，必选）
> 设计并实现多源非结构化数据（DOCX / XLSX / PDF / TXT / MD / 界面截图，共 **173 文件、153MB**）的**零依赖**清洗与脱敏管线：用标准库 `zipfile + XML` 直接解析 DOCX/XLSX、用视觉大模型 OCR **633 张界面截图**（含 DOCX 内嵌图）、按页聚合碎片截图，产出 **121 份 / 105.2 万字符**结构化语料；脱敏覆盖 **8 类规则**（人名 / 公司 / 客户 / 企业主体 / 内部合同号 / 银行账号 / SWIFT / 内网 IP），可复算命中 **4,667 处**，经独立巡检脚本 `audit_leaks.py` 验证**输入侧零残留**（词边界匹配）；进一步**把闸门扩到输出侧**（`sanitize_eval_results.py` 擦除评测产物中编译期派生的真实专名）——三道闸门让公开仓库与简历零合规风险。

### 2. 知识库构建与检索层优化（差异点）
> 基于「编译式知识库」方法论替代传统临时检索 RAG：将 **119 份**清洗语料分批增量编译为结构化 Wiki（**353 概念 + 243 实体 + 74 发现 + 14 高频查询**，共 **819 页**），自动建立 `[[双链]]` 关联与来源追溯。**定位并修复两类检索失效**：① **零召回**——经单变量对照确认是**检索深度（topK 5→15）与问答模型**的共同作用（**并非向量检索**，向量虽配置好、索引也建了 764/817 页，但查询期额度耗尽未生效，已作为**未交付项如实标注**并留一键恢复入口）；② **术语不匹配导致的长尾答偏**——题干说「订单审核通过」而语料说「CP确认」，关键词检索桥接不了；**不改检索器，改用引擎自带的「高频查询页」机制沉淀术语对照**，并用单变量 A/B 验证（**0/5 → 4/5，Fisher 单侧 p=0.024**，两个无关题两臂无差异）。配套 `reingest.py` 一键重建、`resume_ingest.py` 中断续跑、`vector_index.py` 索引批建 + `probe` 自检、`apply_faq_patch.py` 知识固化页幂等注入（可复现）。

### 3. 评测闭环与量化提升（最能体现工程判断，必选）
> 自建 **22 题**评测集（概念 / 对比 / 流程 / 操作 / 报价配比 / 机制六类，含标准答案要点 + 来源标注），通过本地 API 自动跑题并按「命中 / 答偏 / 幻觉 / 零召回」四档判定；命中率 **73.3% → 81.0% → 85.7% → 90.5%** 四轮迭代，**幻觉 0/21**（95% 置信上界 13.3%，带口径限定），**引用可溯源率 100%**。
> **⚠️ 但 90.5% 要连带说清「不可复现」**：同配置再跑两轮都是 **18/21**，且未命中题目几乎不重合 → 对外报 **18~19/21（±1~2 题）** 并附复跑次数。
> 三处关键判断：① **第二、三轮共 4.7pp 的提升，来自修掉评测链路自身的工程缺陷**（网关 502 未重试、项目 ID 解析失效导致全题 404），而非调模型或扩语料；② **第四轮**把问答模型换成 `glm-4.5-air`，端到端 P50 从 61.5s 降到 **18.0s（↓3.4×）**，推翻了「问答必须用旗舰推理模型」的预设——**但代价是 agent 更容易触顶框架 8 步上限**（后测才发现，见下条）；③ **第五轮发现「稳定的是数字、不稳定的是哪几道题」**，于是把主口径从单轮百分比改成「区间 + 复跑次数」。

### 3.5 用「读黑盒」替代「调旋钮」解决框架硬限制（v1.2，最能体现定位能力）
> 应用 agent 有 **8 步工具迭代硬上限**，是头号失分来源（D1 十次采样只命中 1 次）。我先核对了应用配置（`app-state.json`）确认**无步数可配项**，然后**差点走错路**：连续两版报告都在提「换回旗舰模型做对照」——那是拿**模型**这个我调得动的旋钮做文章，而且即便做成，代价是**全部**题多付 3.4× 延迟。
> 真正的突破口是**去读黑盒**：从应用二进制里抠出 agent loop 的系统提示词，发现失败文案自带 `ask it to continue from the latest result`，而**响应里的 `sessionId` 一直躺在我自己的评测数据里**（`events[0]` 就有 `session_id`，我 dump 过却没看见）。
> 于是解变成：**撞上限时带同一 `sessionId` 补一句「请直接给出最终答案」**——实测 **22.8s 拿到完整正确答案**；对照组（不带 `sessionId` 发同一句）答「没有收到具体的问题」，证明答案确实来自会话上下文。**代价只落在撞上限的那部分题。**
> 面试讲法：「这个限制我改不了，但我没去换模型——我先读了它的报错文案和响应字段，发现作者留了逃生口。**答案一直在我已有的数据里，只是我之前没看。**」
>
> ⚠️ **讲这段必须带上后半段，否则就成了自我吹嘘**：A/B 实测 12/15 vs 9/15，**Fisher 单侧 p=0.213，不显著**；
> 而且它把失败性质换了——**续跑关：0 次错误答案 + 6 次无答案；续跑开：2 次错误答案 + 1 次无答案**。
> 对一个以 0 幻觉为卖点的系统，「没答上来」和「答错」不是一回事。**所以我没有把它算作命中率提升。**
> 真正的收获是定位过程本身。而且顺着往下追，**又纠正了一次自己的结论**：
> 我一度写成「这个系统的噪声大于我调过的任何旋钮」（依据是 D1 跨时段 1/10 vs 3/5）。
> 扩样本到 **140 次同配置采样**后，真相比这精确也更有用：
> **不是系统整体噪声大，而是 4 道题处在 8 步上限边缘**（D1 真实作答率 **7/15 ≈ 47%**，
> 5 次采样测出 20% 或 60% 都是正常波动），**其余 18 题 90 次采样零失败**。
> 成因也测出来了：按 `toolEventCount` 分桶，**24~28 桶失败率 93%，≤24 桶 0~13%**（8 步 × ≈3.4 事件/步 ≈ 27）。
> **面试讲法**：「我先说的是『测不准』，后来发现是『这四道题天生贴边』——**前者让人放弃测量，后者给出明确动作**：
> 把对比题的两个概念合并成一页，减少它需要的步数。」

### 4. 落地交付（完整闭环）
> 接入**飞书自建应用机器人**（WebSocket 长连接，免公网服务器）：群内 @机器人 一问一答，卡片消息展示答案 + 来源引用，支持**多轮追问**（复用知识库原生会话）、进度卡片**原地更新**与指数退避重试；内置**用量埋点**（只记元数据不记问题原文）与 `usage_stats.py` 出数。实测群内提问「什么是短溢装」命中评测标准答案。

## 四、项目亮点（技术决策，面试可直接讲）

1. **「先脱敏再入库」的架构判断**：实测证明 LLM 编译会把客户名扩散成独立实体页与索引，事后清理需改动 24+ 个 wiki 页并重建向量索引；因此把脱敏做成入库前的唯一闸门，再用 `audit_leaks.py` 做入库后巡检兜底（双保险）。
2. **零依赖优先**：DOCX/XLSX 解析、清洗、巡检、评测全部只用 Python 标准库，只有 PDF 与飞书 SDK 引入外部依赖——降低环境门槛、便于挂 CI。
3. **归因优先于调参（最值钱的一条）**：命中率不达标时，先怀疑工具链而非模型。实测抓出两个真凶——`currentProject` 为 null 导致 `/projects/current/chat` 全题 404；网关 502 抖动无重试直接判失败。修掉后 O3、O5、C1 三题转命中，命中率 +4.7pp。
4. **换模型前先做对照基准，不靠直觉**：自建 `bench_chat_latency.py` 实测三组配置——`glm-4.5-air` P50 **12.9s**、`glm-4.7` P50 **60.1s**、**`glm-4.7` 关思考链仍 59.5s**。第三组直接证伪了「关掉思考链就能提速」这个最容易想到的假设，把目标锁定为「换模型」而非「调参数」。落地后命中率**不降反升**（85.7% → 90.5%）。
5. **改检索参数必须全量复测**：提高检索深度本是为了修 C3/O4 的零召回，却同时**把 P1 从"答偏"稀释成"拒答"**——**召回更多 ≠ 更好，只盯目标题会漏掉回归。**
6. **踩坑并固化**：重导后失效引用会卡死编译 worker（实测卡 6 小时）→ 在 `reingest.py` 里把「清空引用 wiki 路径的状态文件」写成固定动作；中断续跑固化为 `resume_ingest.py`（file-snapshot 手术法，已编译的不重做）。
7. **知道何时停手**：向量索引有 53 页（25 个词条）因应用侧「以文件名 stem 作向量 ID」而建不上；且查询期接口因额度耗尽调不动。评估后确认这些词条仍能被关键词+图谱召回，**边际收益低 → 主动停止投入**，只记录为遗留项并留一键恢复入口。
8. **脱敏闸门要跟着数据流向走（三道闸门）**：常规做法是「入库前脱敏 + 入库后巡检」两道闸门（扫**输入侧**）。但我发现**检索面变宽**后，`references` 开始带回**编译期从截图 OCR 派生的真实实体页**（真实订单号、配送中心、第三方公司名），从而写进了**入库的评测产物**——**输出侧也漏了**。于是补了第三道闸门 `sanitize_eval_results.py`（`--check` 可挂 CI）。**教训：任何改变"会召回哪些页"的改动，都要重跑输出侧闸门。**
9. **⭐ 给自己纠错：`enabled=true` 不等于生效。** 我一度把这一轮的提升归因于「开了向量检索」——
   配置确实开了、764/817 页索引也确实建成了；但复核发现**查询期的 embedding 调用因账户额度耗尽在静默失败**，
   评测里**一个向量召回事件都没有**。是**单变量对照实验**（两次只差一个变量的运行）把功劳重新分给了
   「检索深度」和「模型」。**沉淀：判断一个开关是否起作用，要看它在下游的数据痕迹，而不是看它自己的状态值；
   并且凡写"某改动带来某效果"，都要能指出那组对照。**

## 五、面试高频问题 + 回答要点

### Q1：为什么用编译式知识库，而不是直接用 RAG / 向量库？
- RAG 是「每次提问临时检索+生成」，用完即弃，知识不积累；编译式是「摄入时编译一次、持续复用」，词条稳定、交叉引用已建好、矛盾主动标记。
- 对「培训知识」这种**结构稳定、需要溯源、需要看全貌**的场景，编译式更合适。
- 简历亮点：体现你对不同知识管理范式的**权衡**，而非只会套 RAG。

### Q2：你的数据脱敏是怎么做的？为什么重要？
- 真实业务数据含人名/客户名/订单号/银行账号，直接上云或写简历有合规风险。
- 做法：人名 →「导师A~E / 学员A~I」、客户 →「客户A/B」、订单号 → `[订单号]`、内网 IP → `[内网地址]`、银行账号/SWIFT → `[银行账号]/[银行代码]`；映射表放本机 `maps_local.py`（gitignore，**脱敏脚本本身不能含明文词表**，否则等于把敏感词公开）。
- 能用结构化正则就别加词条（打地鼠）；英文词必须**忽略大小写 + 词边界**（OCR 大小写不可控、且防 `ABC` 命中 `ABCDEF`）；BIC 码必须锚定 `SWIFT Code：` 上下文，否则误伤 `SHIPPING`、`MATERIAL` 等正常词。
- **最有价值的一点：脱敏要分"输入/输出/派生"三层看，而且词表有天花板。**
  ① **输入侧**（语料）：入库前替换 + 入库后巡检，实测 0 残留；
  ② **输出侧**（产物）：**检索面变宽**后，`references` 开始带回编译期派生的真实实体页（真实订单号、第三方公司名），
  写进了**入库**的评测结果里——于是补了第三道闸门 `sanitize_eval_results.py`；
  ③ **派生侧**（无法用词表拦）：模型会**推断**出输入里没有的信息——语料里地址已脱敏成 `[地址]`，
  它却凭银行地址里的**城市线索**用**世界知识**补出"所在国家：某南亚国家"。**这类残留只能靠巡检发现 + 人工判断，词表永远挡不住。**
  这三层认知是我做完这个项目才形成的。
- **⭐ 再补一条更狠的（2026-09-13）：闸门自己也会漏，而且三道门会因为「共用一张词表」一起漏。**
  我的入库反扫、产物擦除、题集护栏其实都在跑，但**词表只收录「已经撞见过一次的」形态**——
  一个从没进过词表的真实客户名，就这样通过三道门、**随公开提交上线了**（在 3 个入库文件里）。
  修法不是再加一条词（那还是打地鼠），而是**换判据**：
  题集护栏从「标题含连续 ≥5 位数字」改成**「标题里一个中文都没有 → 一律排除」**（新增第二层），
  擦除闸门从单一手工清单改成**「手工清单 + 完整真实词表」两层**（ASCII 走词边界防误报）。
  教训一句话：**当你的检测器和被检测对象共用同一份知识时，它的盲区就是你的盲区。**
- 强调"合规意识 + 工程化"，这是加分项。

### Q3：检索命中率/准确率这些数字怎么来的？
- 自建评测集（22 题，从语料提炼真实问题 + 标准答案要点），脚本逐条调本地 API 提问，按「命中/答偏/幻觉/零召回」四档判定。
- 关键：能说清楚**评测集怎么建、判定标准是什么**，比数字本身更重要。
- 加分细节：设计新题前先用原始语料交叉校验编译页，避免把编译错误固化成"标准答案"；口径矛盾的题（P2）标注为**不计分项**，而不是硬凑正确率。

### Q4：国产大模型（智谱 GLM）接入有什么坑？
- OpenAI 兼容接口，base_url + key + 模型名三步接入。
- 实测踩坑：模型列表接口不完整；免费 flash 限流严格（code 1302）；**推理型模型**编译极慢（66.6s/次）；账号并发≈1，编译与评测会互相抢占 → 必须串行。

- **有趣的反直觉点**：我原以为"快模型质量会差一些"，实测**命中率不降反升**（85.7%→90.5%）——因为一问一答场景里，`glm-4.7` 的长思维链未必都用在答案上。**别把"旗舰=更好"当默认假设，要做对照实验。**

### Q5：机器人为什么选飞书？有什么工程坑？
- 飞书**个人账号即可建企业自建应用**，走 WebSocket 长连接收消息，**免公网服务器、发布免审核**；企微机器人仅限内部群。

### Q7：命中率是怎么一步步提上去的？（**别只讲 90.5%，必须讲它不可复现**）
> 数字达标后，问题从"为什么这么低"变成"你怎么提上去的"——**讲归因链条比讲结果重要**。
> ⚠️ **开场就把口径摆正**：「90.5% 是单轮最好成绩；同配置再跑两轮都是 18/21，所以我对外报 **18~19/21**。」
> **先把最不利的事实说出口，后面所有数字才可信。**

| 轮次 | 语料覆盖 | 检索 / 模型 | 题数 | 命中率 | 幻觉率 | 关键动作 |
|---|---|---|---|---|---|---|
| 基线 09-10 | 12 份（19%） | 关键词+图谱 / glm-4.6 | 15 | 73.3% | 0% | 首版评测；缺口定位为语料未覆盖 |
| v0.2 09-12 | **119 份（100%）** | 关键词+图谱 / glm-4.7 | 22 | 81.0% | 0% | 语料扩容 10×；但 O3/O5 因 502 丢分、C1 零召回 |
| v0.3 09-12 | 119 份 | 关键词+图谱 / glm-4.7 | 22 | 85.7% | 0% | **修评测链路自身缺陷**：502 指数退避重试 + 项目 ID 解析；3 题转命中 |
| **v1.0 09-12** | 119 份 | **关键词+图谱 / glm-4.5-air** | 22 | **90.5%** | **0%*** | **两项 P0：检索深度 topK 5→15 + 换快模型** |
| **v1.1 09-12** | 119 份 + 1 页沉淀 | 同上 | 22 | **85.7%**（两轮均 18/21） | 0% | **P1 知识固化 + 稳定性采样**；**并发现 90.5% 不可复现** |

- **关键句 1**：「+4.7pp 不是调参调出来的，是先排除了工具链问题——评测脚本走 `/projects/current/chat`，而 `currentProject` 为 null 时该端点 404；网关 502 抖动无重试直接判失败。修掉这两个，O3、O5、C1 自然就命中了。」
- **关键句 2**：「第四轮的 +4.8pp，我一开始**归因错了**——以为是开了向量检索。后来复核发现向量那一路**全程没生效**（配置和索引都"成"了，但查询期 embedding 因额度耗尽失败，评测里一个向量召回事件都没有）。是**单变量对照实验**把功劳重新分给了**检索深度 topK 5→15**：原先偶发零召回的两题（短溢装、色码明细）转为稳定命中；同时换掉问答模型，延迟降了 3.4 倍、命中率还升了。」
- **归因分布（v1.1 更新）**：未命中的题里**始终 0 题是语料缺失**——① **P1 已修复**：根因是**术语不匹配**（题干「订单审核通过」↔ 语料「CP确认」），答案页从未进过引用；**不改检索器，改用引擎自带的「高频查询页」沉淀术语对照**，单变量 A/B **0/5 → 4/5**（Fisher 单侧 p=0.024），两个无关题两臂无差异；② **D1/D2 是应用框架的 8 步迭代上限**——**且它已取代知识缺口成为第一大失分来源**：D1 十次采样命中 **1/10**。注意：**这不是「退化」，是此前没测过基线**（v1.0 那一次命中大概率就是 1/10 里的那一次），我曾把它归因为「换快模型」，**该归因无对照、已撤回**。
- **反直觉的坑 1**：**检索深度调大不是免费的**——topK 从 5 提到 15 修好了 C3/O4 的零召回，却把 P1 的答案页挤出/淹没了排序。**改检索参数必须全量复测，不能只盯目标题。**
- **反直觉的坑 2（v1.1，比坑 1 更值钱）**：**"稳定"的可能是数字，不是题目。** 两轮都跑出 18/21，看着很稳；把未命中清单一摆——r1 是 D1/D2/P1，r2 是 D1/P3/O2，**几乎不重合**。所以单轮百分比会骗人：**必须跑多轮、并对摇摆题单独采样**，否则你会把一个运气好的数字当成能力。
- **关键句 3（v1.1）**：「修长尾题我不改检索器——那是我动不了的。我用引擎自带的『高频查询页』机制把术语对照沉淀成一页知识，然后做单变量 A/B：只切这一页在不在，**0/5 → 4/5**，而且两个无关题在两臂**没有差异**，这才敢说这页有效、不是环境波动。」
- `*` 幻觉率 0% 是**本次 21 题采样**结果，不等于"从不编造"：P1 在 topK=15 下出现过**轻度编造倾向**（写出语料里没有的流程描述），已按"答偏"而非"安全拒答"归类——口径见 Q8。

### Q8：项目才一个多月（甚至不到两周），幻觉率就做到 0%？可信吗？
> ⚠️ **最危险的一问**。应对策略：**不辩解，主动把口径收紧**——自曝指标缺陷反而建立可信度。

**面试官其实问了两件事，必须分开答**

| 质疑 | 本质 | 接法 |
|---|---|---|
| 「一个月？」 | 时间/工作量 | 拆时间线：语料是实习期积累的，引擎非自研，工作量在管线与评测 |
| 「0%？」 | 数字可信度 | 拆口径：架构副产品 + 小样本，统计上不能写成 0% |

**A. 时间线（30 秒）**
- 语料是**实习培训期积累**的真实业务数据（173 文件 / 153MB），不属于项目周期内产出。
- 知识库引擎用现成方案，**不从零造轮子**；我的工作量在数据管线、评测闭环、机器人集成。
- 真正卡时间的是 119 份语料的**编译排队**（glm-4.7 实测 66.6s/次，全量约 24h，实际跑了一整夜），不是人力。

**B. 数字（核心，建议背）**
1. **「0% 不是优化出来的，是架构的副产品」**——非通用 chatbot，问答强制 grounded，每条答案必须挂来源页，检索不到就不生成。等于"编造"在设计阶段就被挡住，**我没有做"幻觉抑制"这个调优动作，所以不需要时间调它**。
2. **「0/21 统计上不该写成 0%」**——0/N 的 95% 置信上界 = `1 - 0.05^(1/N)`：

   | N（全 0 幻觉） | 95% 置信上界 |
   |---|---|
   | 15（基线） | 18.1% |
   | **21（当前）** | **13.3%** |
   | 60 | 4.9% ← 要支撑「<5%」的最低题量 |
   | 100 | 3.0% |

   即：**21 题全零幻觉，只能负责任地说「真实幻觉率 < 13.3%」**。
3. **主动暴露盲区并已补齐（终结追问的一句）**：零幻觉有个捷径是「不会就拒答」——所以光有 0 幻觉不够，必须证明**拒答本身是有判断的**。我随后做了专项测试（8 道语料外问题 + 5 道语料内冷门对照）：语料外 **8/8 正确拒答、0 编造**；语料内 **5/5 正常作答、0 误拒**。更关键的是，8 道语料外题里有 **7 道检索都返回了内容**（5~15 条），模型仍正确拒答——说明它靠的是**内容相关性判断**，而不是「检索不到就拒答」。样本量偏小（8 题，95% 置信下界 68.8%），已在报告里如实标注。

**C. 简历 bullet 写法**
- ❌ 写「幻觉率 0%」——绝对化、无样本量，面试极易被击穿。
- ✅ 写「**幻觉 0/21（95% 置信上界 13.3%）**」——同时证明你会算、敢认、懂统计口径。
- 若被追问「13.3% 怎么来的」：0 事件的 Clopper–Pearson 单侧上界 `1-α^(1/n)`，α=0.05，n=21；工程上可用「三倍律」粗估 `3/n ≈ 14%`。

**D. 别踩的坑**
- 别说「我们模型好所以不幻觉」——把功劳推给模型，等于承认自己没做事。
- 别说「测试题比较简单」——自贬。正确说法是「当前题目集中在语料内有明确答案的事实题，样本量仍需扩到 60+ 才能支撑更严格的门槛」。
- 别在 0% 上加码（如「完全消除了幻觉」）——每加一句绝对化表述，就多一个被击穿的点。

### Q9：响应要 60 多秒，这东西能用吗？
> 一定会问。**上一轮这是明确未达标的项**——现在已大幅改善，回答时**要先给新数字，再承认仍未达标**。

- **先给新数字**：端到端 P50 **18.0s**（上一轮 61.5s，**↓3.4×**），均值 22.1s、P90 31.6s。
  做法是**先做对照基准再动手**：`glm-4.5-air` P50 12.9s vs `glm-4.7` 60.1s，且覆盖度更高（0.862 vs 0.805）→ 切模型。
- **主动说清"关思考链没用"**：我原本以为 `glm-4.7` 慢是因为长思维链，实测**关掉思考链 P50 仍是 59.5s**——
  慢的是模型本身，所以必须换模型，而不是调参数。**先证伪最容易想到的开关，省下无效尝试。**
- **承认仍未达标**：18.0s 距 <3s 目标仍有一个量级，且是架构性 trade-off
  （编译式检索 + 长答案生成 + 本地 API 单并发串行）。这条**如实写进了报告**，没有隐去。
- **讲用户感知**：飞书机器人不是干等——先回「正在查询」卡片、进度**原地更新**，用户看到的是持续反馈而非白屏。
- **再给优化路径**：① 答案缓存（培训知识更新频率低，命中率会很高）；② 流式输出；③ 继续收敛检索往返次数。
- **加分句**：「延迟和质量是 trade-off，上一轮我选了质量优先并把延迟作为已知差距写进报告；这一轮我用**对照基准**证明了这个 trade-off 比预期宽松——换快模型后延迟降 3.4 倍、命中率还升了 4.8pp。」

> ⚠️ **不要因为提速了就开始说"秒级"**：18s 仍是"十几秒级"，价值点是
> **「10~30 分钟且可能找不齐」→「十几秒且每条结论可点回来源页」**。

> **后注（如果被追问"还有没有别的不稳定"）**：有一题（D2 待核单 vs 已核单）在单轮评测里撞上了**应用框架的 8 步工具迭代上限**，
> 没产出答案；但检索本身是对的（两个页面都召回了），**复跑 3 次有 2 次答对**——属偶发、非能力缺失。
> 我把这个也写进了报告，并且**主口径仍按单轮实测的 90.5% 报，没有按复跑的 95.2% 报**。


### Q10：这和「LangChain + 向量库跑个 demo」有什么区别？
- **知识是资产而非中间态**：编译产物是 819 页结构化 Wiki，人可以直接读、可以纠错、可以做知识治理；临时 RAG 的检索结果是"用完即弃"的。
- **可溯源是硬约束**：每条答案强制挂来源页，引用可溯源率 **100%**，幻觉 0/21。
- **检索不是只有向量**：我这套是**关键词 + 向量 + 图谱（1-hop 双链）的混合检索**，而不是"向量库一条路"——向量只是其中一路（764/817 页有向量索引），另外两路负责兜住字面精确匹配与关联跳转。
- **有量化闭环**：22 题主评测集（命中率/幻觉率/溯源率）+ **13 题拒答专项**（8 语料外 + 5 语料内对照）+ **稳定性复跑**（同题 3 次）+ **延迟对照基准**（3 组配置）+ 脚本化跑题 + 分档判定 + 四轮迭代归因，改语料/换模型后一键复跑对比。
- **有合规设计**：入库前脱敏 + 入库后巡检双闸门，4,667 处命中、零残留。
