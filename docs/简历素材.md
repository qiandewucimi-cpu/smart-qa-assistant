## 一、项目一句话定位

> 基于「编译式知识库」的企业培训智能问答助手：把散落在聊天记录、会议纪要、在线文档里的培训知识，自动编译成可溯源、可互链的结构化 Wiki，实现「一句话检索 + 引用溯源」，解决新人找资料难、重复提问多的痛点。

**技术栈标签**：LLM Wiki（Karpathy 编译式方法论）｜ 智谱 GLM-4.6（国产大模型）｜ RAG / 知识图谱 ｜ 飞书/企微机器人

## 二、核心 bullet（STAR 结构，可挑 3~4 条）

### 1. 数据工程（最硬核、最值得讲）
> 设计并实现多源非结构化数据（聊天记录 / 会议纪要 / DOCX / PDF，共 173 文件、153MB）的清洗与脱敏管线：零依赖解析 DOCX（标准库 zipfile + XML）、人名/客户/订单号等敏感信息脱敏 **1512 处**、达成全项目**零残留**，在合规前提下把真实业务数据转化为可用语料。

### 2. 知识库构建（差异点）
> 基于 Karpathy「LLM Wiki」方法论，用编译式方案替代传统临时检索 RAG：将 64 份清洗后语料增量编译为结构化知识库（**Y 个实体 + Z 个概念** + 知识图谱），自动建立 `[[双链]]` 关联与来源追溯，知识只编译一次、持续复用。

### 3. 检索与评测（量化能力）
> 构建 15 题评测集（覆盖概念/对比/流程/操作四类），量化验证检索命中率 **≥85%**、答案准确率 **≥80%**、幻觉率 **≤5%**，并对比向量检索开启前后的召回提升。

### 4. 落地交付（完整闭环）
> 接入飞书 / 企业微信聊天机器人，落地到真实群聊场景；新人找资料平均耗时从 X 分钟降至 Y 秒。

## 三、面试高频问题 + 回答要点

### Q1：为什么用 LLM Wiki 而不是直接用 RAG / 向量库？
- RAG 是「每次提问临时检索+生成」，用完即弃，知识不积累；LLM Wiki 是「摄入时编译一次、持续复用」，词条稳定、交叉引用已建好、矛盾主动标记。
- 对"培训知识"这种**结构稳定、需要溯源、需要看全貌**的场景，编译式更合适。
- 简历亮点：体现你对不同知识管理范式的**权衡**，而非只会套 RAG。

### Q2：你的数据脱敏是怎么做的？为什么重要？
- 真实业务数据含人名/客户名/订单号，直接上云/写简历有合规风险。
- 做法：人名→「导师A~E/学员A~F」、客户→「客户A/B」、订单号→`[订单号]`、内网IP→`[内网地址]`；DOCX 用标准库零依赖解析（不依赖 python-docx，是个加分点）。
- 强调"合规意识"，这是加分项。

### Q3：检索命中率/准确率这些数字怎么来的？
- 自建评测集（15 题，从语料提炼真实问题 + 标准答案要点），逐条在知识库上提问，按「命中/答偏/幻觉」三类判定。
- 关键：能说清楚**评测集怎么建、判定标准是什么**，比数字本身更重要。

### Q4：国产大模型（智谱 GLM）接入有什么坑？
- OpenAI 兼容接口，base_url + key + 模型名三步接入。
- 实测踩坑：模型列表接口不完整（部分可用模型不返回）、免费 flash 模型限流严格（code 1302）、带推理模型（glm-4.6 reasoning）编译偏慢。→ 选型从"免费 flash"换成"付费 glm-4.6"。

### Q5：这个项目如果上线，会遇到什么工程问题？
- 知识更新（新人文档持续产出 → 增量摄入 + Source Watch 自动监控）
- 权限隔离（不同岗位看不同知识）
- 并发/成本（大批量编译的 token 成本与速率控制）
- 能答出这些，说明你思考了"demo → 生产"的差距。
