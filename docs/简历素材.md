## 一、项目一句话定位

> 基于「编译式知识库」的企业培训智能问答助手：把散落在聊天记录、会议纪要、在线文档里的培训知识，自动编译成可溯源、可互链的结构化 Wiki，实现「一句话检索 + 引用溯源」，解决新人找资料难、重复提问多的痛点。

**技术栈标签**：LLM Wiki（Karpathy 编译式方法论）｜ 智谱 GLM（国产大模型）｜ RAG / 知识图谱 ｜ 飞书长连接机器人 ｜ 多模态（GLM-4V 截图 OCR）

## 二、核心 bullet（STAR 结构，可挑 3~4 条）

### 1. 数据工程（最硬核、最值得讲）
> 设计并实现多源非结构化数据（聊天记录 / 会议纪要 / DOCX / XLSX / PDF / 界面截图，共 173 文件、153MB）的**零依赖**清洗与脱敏管线：用标准库 `zipfile + XML` 解析 DOCX/XLSX、用视觉大模型 OCR 566 张界面截图（含 DOCX 内嵌图 499 张）、把碎片截图按页聚合，最终产出 **121 份 / 105.2 万字符**结构化语料；脱敏覆盖 **8 类规则**（人名 / 公司 / 客户 / 企业主体 / 内部合同号 / 银行账号 / SWIFT / 内网 IP），可复算命中 **4,667 处**，并经独立巡检脚本达成全项目**零残留**——在合规前提下把真实业务数据转化为可用语料。

### 2. 知识库构建（差异点）
> 基于 Karpathy「LLM Wiki」方法论，用**编译式**方案替代传统临时检索 RAG：将 119 份清洗语料分批增量编译为结构化知识库（**X 个实体 + Y 个概念** + 规则页 + 知识图谱），自动建立 `[[双链]]` 关联与来源追溯；知识只编译一次、持续复用，并配 `reingest.py` 一键重建、`Source Watch` 监听源文件变化。

### 3. 检索与评测（量化能力）
> 构建 **22 题**评测集（覆盖概念 / 对比 / 流程 / 操作 / 报价配比 / 机制六类，带标准答案要点 + 来源标注），通过本地 API 自动跑题、按「命中 / 答偏 / 幻觉 / 拒答」四档判定；batch1 基线：命中 11/15、**幻觉 0/15（95% 置信上界 18.1%）**、引用可溯源率 100%；全量编译后目标命中率 **≥85%**（缺口已定位为语料覆盖度而非检索质量）。评测口径与门槛对标见 `docs/质量门槛对标.md`。
>
> ⚠️ **不要写「幻觉率 0%」**——绝对化且无样本量，面试极易被击穿。写「0/15（置信上界 18.1%）」。详见 §四 Q8。

### 4. 落地交付（完整闭环）
> 接入**飞书自建应用机器人**（WebSocket 长连接，免公网服务器）：群内 @机器人 一问一答，卡片消息展示答案 + 来源引用，支持**多轮追问**（复用知识库原生会话）、进度原地更新与超时重试；新人找资料平均耗时从 X 分钟降至 Y 秒。

## 三、项目亮点（技术决策，面试可直接讲）

1. **「先脱敏再入库」的架构判断**：实测证明 LLM 编译会把客户名扩散成独立实体页与索引，事后清理需改动 24+ 个 wiki 页并重建向量索引；因此把脱敏做成入库前的唯一闸门，并加 `audit_leaks.py` 做**入库后巡检兜底**（双保险）。
2. **零依赖优先**：DOCX/XLSX 解析、清洗、巡检、评测全部只用 Python 标准库，只有 PDF 与飞书 SDK 引入外部依赖——降低环境门槛、便于 CI。
3. **编译速度瓶颈定位与量化**：自建 `bench_models.py` 对比模型耗时，定位「九成输出是思维链」的推理模型是瓶颈（单次 66.6s），并给出「入库用快模型、聊天用强模型」的分路由方案。
4. **踩坑并固化**：重导后失效引用会卡死编译 worker（实测卡 6 小时）→ 在 `reingest.py` 里把「清空引用 wiki 路径的状态文件」写成固定动作。

## 四、面试高频问题 + 回答要点

### Q1：为什么用 LLM Wiki 而不是直接用 RAG / 向量库？
- RAG 是「每次提问临时检索+生成」，用完即弃，知识不积累；LLM Wiki 是「摄入时编译一次、持续复用」，词条稳定、交叉引用已建好、矛盾主动标记。
- 对"培训知识"这种**结构稳定、需要溯源、需要看全貌**的场景，编译式更合适。
- 简历亮点：体现你对不同知识管理范式的**权衡**，而非只会套 RAG。

### Q2：你的数据脱敏是怎么做的？为什么重要？
- 真实业务数据含人名/客户名/订单号/银行账号，直接上云或写简历有合规风险。
- 做法：人名 →「导师A~E / 学员A~I / 外部人员A~E」、客户 →「客户A/B」、订单号 → `[订单号]`、内网 IP → `[内网地址]`、银行账号/SWIFT → `[银行账号]/[银行代码]`；映射表放本机 `maps_local.py`（gitignore，**脱敏脚本本身不能含明文词表**，否则等于把敏感词公开）。
- 能用结构化正则就别加词条（打地鼠）；英文词必须**忽略大小写 + 词边界**（OCR 大小写不可控、且防 `ABC` 命中 `ABCDEF`）。
- 强调"合规意识 + 工程化"，这是加分项。

### Q3：检索命中率/准确率这些数字怎么来的？
- 自建评测集（22 题，从语料提炼真实问题 + 标准答案要点），脚本逐条在知识库上提问，按「命中/答偏/幻觉」三类判定。
- 关键：能说清楚**评测集怎么建、判定标准是什么**，比数字本身更重要。
- 加分细节：设计新题前先用原始语料交叉校验编译页，避免把编译错误固化成"标准答案"。

### Q4：国产大模型（智谱 GLM）接入有什么坑？
- OpenAI 兼容接口，base_url + key + 模型名三步接入。
- 实测踩坑：模型列表接口不完整；免费 flash 限流严格（code 1302）；**推理型模型**（思考链占九成输出）编译极慢（单次 66.6s）；账号并发≈1，编译与评测会互相抢占 → 必须串行。

### Q5：你的机器人为什么选飞书？有什么工程坑？
- 飞书**个人账号即可建企业自建应用**，走 WebSocket 长连接收消息，**免公网服务器、发布免审核**；企微机器人仅限内部群。
- 工程坑：飞书要求「收到事件 3 秒内返回」否则重推 → 回调只入队，问答放后台单 worker 串行（同时规避账号并发≈1）；先回「正在查询」卡片、答案就绪后**原地更新**，体验更好。

### Q6：这个项目如果上线，会遇到什么工程问题？
- 知识更新（新人文档持续产出 → 增量摄入 + Source Watch 监控）
- 权限隔离（不同岗位看不同知识）
- 并发/成本（大批量编译的 token 成本与速率控制）
- 能答出这些，说明你思考了"demo → 生产"的差距。

### Q8：项目才一个多月（甚至不到两周），幻觉率就做到 0%？这数字可信吗？
> ⚠️ **最危险的一问**：`0%` 绝对化 + 无样本量 + 时间极短，三者叠加极易被判定为「编的」。
> 应对策略：**不辩解，主动把口径收紧**——自曝指标缺陷反而建立可信度。

**先厘清：面试官其实问了两件事，必须分开答**

| 质疑 | 本质 | 接法 |
|---|---|---|
| 「一个月？」 | 时间/工作量 | 拆时间线：语料来自实习期积累，引擎非自研，工作量在管线与评测 |
| 「0%？」 | 数字可信度 | 拆口径：是架构副产品 + 小样本，统计上不成立，主动给置信上界 |

**A. 时间线（30 秒）**
- 语料是**实习培训期积累**的真实业务数据（173 文件 / 153MB），不属于项目周期内产出。
- 知识库引擎用现成的编译式 Wiki，**不从零造轮子**；我的工作量在数据管线、评测闭环、机器人集成。
- 真正卡时间的是 119 份语料的**编译排队**（glm-4.7 实测 66.6s/次，全量约 24h），不是人力。
- 📌 **简历层面直接消解**：时间写 `2026.06–至今`，或 `2026.09–至今（语料为 2026.06–08 实习期积累）`。更准确，也更好看。

**B. 数字（核心，建议背）**
1. **「0% 不是优化出来的，是架构的副产品」**——非通用 chatbot，问答强制 grounded，每条答案必须挂来源页，检索不到就不生成。等于"编造"在设计阶段就被挡住，**我没有做"幻觉抑制"这个调优动作，所以不需要时间调它**。
2. **「0/15 统计上不该写成 0%」**——0/N 的 95% 置信上界 = `1 - 0.05^(1/N)`：

   | N（全 0 幻觉） | 95% 置信上界 |
   |---|---|
   | 15（当前 batch1） | **18.1%** |
   | 22（规划评测集） | 12.7% |
   | 60 | 4.9% ← 要支撑「<5%」的最低题量 |
   | 100 | 3.0% |

   即：**只有 15 题时，只能负责任地说「真实幻觉率 < 18%」**。
3. **主动暴露盲区（终结追问的一句）**：零幻觉有个捷径是「不会就拒答」。若不单独测**拒答准确性**，0% 就是脏的 —— 已规划「语料外问题」子集补测（对齐 `docs/质量门槛对标.md` 差距 #2）。

**C. 简历 bullet 改写建议**

- ❌ 现写法：「batch1 首轮达成**幻觉率 0%**」——绝对化、无样本量、与目标混写。
- ✅ 改写法：「构建 22 题评测集（六类，含标准答案要点 + 来源标注），自动跑题并按「命中/答偏/幻觉/拒答」四档判定；batch1 基线：命中 11/15、**幻觉 0/15（95% 置信上界 18.1%）**、引用可溯源率 100%，全量 121 份语料编译后重测中。」

> 💡 写「0/15（置信上界 18.1%）」比写「0%」**强得多**：同时证明你会算、敢认、懂统计口径。
> 一旦面试官追问「18.1% 怎么来的」，答：0 事件的 Clopper–Pearson 单侧上界 `1-α^(1/n)`，α=0.05，n=15；工程上可用「三倍律」估算 `3/n ≈ 20%`。

**D. 别踩的坑**
- 别说「我们模型好所以不幻觉」——把功劳推给模型，等于承认自己没做事。
- 别说「测试题比较简单」——自贬。正确说法是「当前题目集中在语料内有明确答案的事实题，覆盖面是下一步要扩的」。
- 别在 0% 上加码（如「完全消除了幻觉」）——每加一句绝对化表述，就多一个被击穿的点。

### Q7：你的命中率只有 73%，是不是说明系统不行？
> 这是最可能被追问的一问，答好是加分项。详细对标见 `docs/质量门槛对标.md`。

- **先讲口径**：73.3% 是在**只导入 19% 语料（12/64 份）**、15 道题上测出的**中间快照**，不代表系统水平；语料补齐到 121 份后正在重测。
- **再讲归因**：4 道未命中里——O3 答案在未导入的 xlsx（**纯覆盖问题**）、C2/C4 是"答了但关键粒度不够"、P2 是**原始语料两处自相矛盾**。至少 2~3 道是语料问题，不是模型/检索能力问题。
- **再讲企业真正看什么**：企业最怕的不是"答不出"，而是"答错还自信"。**幻觉率 0%、答案 100% 带来源引用**才是上线底线，这项已达标（且是最难的一环）。
- **最后讲闭环**：定位到瓶颈在**覆盖度而非模型**，于是把语料扩了 10 倍，而不是盲目换模型/调参——这个判断本身就是能力体现。
- **补一句计划**：全量编译后重跑 22 题，并新增"语料外问题"子集补测**拒答准确性**（0 幻觉 ≠ 会拒答，这是当前真实盲区）。
