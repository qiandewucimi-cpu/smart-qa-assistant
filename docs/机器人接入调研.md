## 1. 平台对比：飞书 vs 企业微信

| 维度 | 飞书 | 企业微信 |
|---|---|---|
| 个人账号能否建机器人 | ✅ 可创建「企业自建应用」，无需企业认证 | ⚠️ 需企业主体；个人较难 |
| 收消息方式 | ✅ WebSocket 长连接（免公网） | ⚠️ 回调需公网 URL 或自建 |
| 群聊触发 | ✅ 群内 @机器人 可触发 | ⚠️ 官方机器人仅**内部群**，外部群/个人微信不支持 |
| 群机器人 Webhook | 可发可收（自建应用） | ❌ 只能**发**，不能收（无法做问答） |
| 智能机器人 API | — | 2026-05 起可收 @消息，但仅限**内部群** |
| 发布审核 | ✅ 个人应用「免审核」发布 | ⚠️ 受企业管理员管控 |

**结论**：本项目是个人简历项目、服务对象大概率是「自己 + 少数熟人」的外部小群，企业微信官方能力在此场景基本不可用；飞书是唯一顺畅路径。

## 2. 飞书接入方案（推荐）

### 2.1 为什么选飞书

1. **零公网成本**：长连接（WebSocket）模式让本地进程直接订阅事件，无需注册域名、无需 HTTPS 回调、无需加密策略。
2. **个人可自建应用**：飞书开发者后台允许个人账号创建「企业自建应用」。
3. **发布免审核**：自建应用发布「本次发布免审核，提交后即可上线」。
4. **生态成熟**：官方 Python SDK（`lark-oapi`）对长连接支持完善。

### 2.2 关键事实（来自飞书开放平台官方文档）

- 长连接模式**不支持商店应用**，必须用「企业自建应用」。
- 长连接接收事件**必须先在本地把客户端跑起来**（有长连接在线），后台才能保存订阅方式。
- 需要应用凭证：**App ID** + **App Secret**（在「凭证与基础信息」页查看）。

### 2.3 配置步骤（六步）

| 步骤 | 操作 | 位置 |
|---|---|---|
| 1 | 登录飞书开放平台，**创建企业自建应用**（填名称如「智能问答助手」） | open.feishu.cn → 开发者后台 |
| 2 | 记录 **App ID / App Secret** | 应用 → 凭证与基础信息 |
| 3 | **添加应用能力 → 机器人** | 应用 → 应用能力 |
| 4 | 开通权限（见 2.4） | 应用 → 开发配置 → 权限管理 → API 权限 |
| 5 | **事件订阅**：订阅方式选「使用长连接接收事件」，添加事件 `im.message.receive_v1` | 应用 → 事件与回调 → 事件配置 |
| 6 | **创建版本并发布**（个人应用免审核） | 应用 → 版本管理与发布 |

> 注意顺序：先跑通本地长连接客户端（步骤 5 前半），后台检测到长连接在线后，才能成功保存「使用长连接接收事件」。

### 2.4 权限清单（API 权限）

| 权限 scope | 用途 | 必选 |
|---|---|---|
| `im:message.p2p_msg:readonly` | 读取用户发给机器人的**单聊**消息 | ✅ |
| `im:message.group_at_msg:readonly` | 接收群聊中 **@机器人** 的消息事件 | ✅ |
| `im:message:send_as_bot` | 以机器人身份**回复/发消息** | ✅ |
| `im:chat:readonly` | 获取群信息（可选） | 可选 |
| `contact:user.id:readonly` | 获取用户 ID（显示提问人昵称，可选） | 可选 |

> 也可用「批量导入权限」粘贴 JSON 一次性开通，避免逐项点选。

### 2.5 事件清单

| 事件类型 | 触发时机 |
|---|---|
| `im.message.receive_v1` | 收到发给机器人/群内 @ 机器人的消息 |

## 3. 与 LLM Wiki 对接架构

### 3.1 推荐：本地 HTTP API 直连

机器人进程与 LLM Wiki 同机运行，直接调本地 HTTP API，**不需要额外中间层**：

```
用户（飞书群）
   │  @机器人 提问
   ▼
飞书服务器 ──WebSocket 长连接──▶ 本地机器人进程（Python，lark-oapi）
   │                                    │
   │                                    │ ① 解析问题
   │                                    ▼
   │                            LLM Wiki HTTP API（127.0.0.1:19828）
   │                            POST /api/v1/projects/current/chat
   │                                    │ ② 内置 Agent：检索 + glm-4.6 生成 + 引用
   │                                    ▼
   │                            答案 + references[]
   │                                    │
   │ ◀──回复消息 API（send/reply）──────┘ ③ 把答案+来源发回群
   ▼
用户看到答案（附来源引用）
```

### 3.2 已有基础（关键复用点）

本项目的 `scripts/eval_chat.py` **已经跑通了同一调用链**，机器人只需复用同样的 HTTP 客户端逻辑：

```python
# 与 eval_chat.py 完全一致的调用模式
POST http://127.0.0.1:19828/api/v1/projects/current/chat
Authorization: Bearer <LLM_WIKI_API_TOKEN>   # 已存于 scripts/.env（不入库）
Content-Type: application/json
{"message": "什么是「短溢装」？", "stream": false}

# 响应（v0.6.11 实测结构）
{ "message": { "content": "最终答案文本..." },
  "references": [ { "path": "...", "title": "...", "score": ... } ],
  "usage": { ... } }
```

可复用的端点（完整清单见官方 API 参考）：

| 端点 | 方法 | 用途 |
|---|---|---|
| `/api/v1/health` | GET | 探活（无需鉴权） |
| `/api/v1/projects` | GET | 列出项目（可定位 current） |
| `/api/v1/projects/{id}/chat` | POST | **RAG 问答**（机器人主用） |
| `/api/v1/projects/{id}/search` | POST | 混合检索（BM25 + 向量），需要展示检索片段时用 |
| `/api/v1/projects/{id}/graph` | GET | 知识图谱（可视化扩展） |

### 3.3 外部可控边界（结论：能读、能问、能触发，**不能写**）

LLM Wiki 自带 `tools/llm-wiki/mcp-server/`（`llm-wiki-mcp`）与本地 HTTP API（`/api/v1`），二者是**同一个后端的两张皮**，暴露的能力完全一致。

**完整外部工具面（MCP 11 个工具 + 对应 HTTP 端点，v0.6.11 实读源码）**：

| MCP 工具 | 等价端点 | 能做什么 |
|---|---|---|
| `llm_wiki_status` | `GET /health` | 探活 |
| `llm_wiki_projects` | `GET /projects` | 列项目、定位 current |
| `llm_wiki_set_project` | —（MCP 侧绑定） | 把 MCP 会话钉到某项目 |
| `llm_wiki_files` | `GET /files` | 列文件树（`wiki`/`sources`） |
| `llm_wiki_read_file` | `GET /files/content` | **读**单页（仅 `wiki/`、`raw/sources/` 等公开路径） |
| `llm_wiki_reviews` | `GET /reviews` | 列审阅项（missing-page/duplicate/contradiction…） |
| `llm_wiki_search` | `POST /search` | 关键词/向量检索 |
| `llm_wiki_chat` | `POST /chat` | **RAG 问答**（内置 Agent 检索 + 生成 + 引用） |
| `llm_wiki_graph` | `GET /graph` | 查知识图谱 |
| `llm_wiki_rescan_sources` | `POST /sources/rescan` | **触发**源目录重扫（即触发 app 自己的解析+编译） |
| `llm_wiki_embed_page` | `POST /pages/embed` | 给**已存在**的 md 页建/重建向量索引 |

> **关键结论（回答「解析能不能挪到外部」）**：外部接口里**没有任何「写入页面 / 导入文档 / 上传资料」的端点**。唯一的入库通道是「把文件放进 `raw/sources/` → 触发 `rescan`」，之后由 **LLM Wiki 自己的 Agent** 完成解析与编译。外部能做的是**读、查、问、触发**；**写与编译被刻意关在应用内**。

**为什么设计成这样**：编译 Agent 不只「写 md」，它还负责交叉引用、`index.md`/`log.md` 维护、`review.json` 审阅队列、以及 `ingest-cache.json` / `file-snapshot.json` 的 hash 记账。绕过它直接写 `wiki/*.md`（物理上可行，因为 wiki 就是 Obsidian vault 里的一堆明文 md）会立刻丢掉这四件事，并制造状态不一致——本项目已实测过：重导后残留的失效引用直接把 worker 卡死 6 小时。

**本项目的取舍**：机器人走 HTTP API（直连 `/chat`）；MCP 保留给「把 Wiki 作为工具挂进外部 Agent（如 Claude Code）」的场景。但无论走哪条，**编译永远在 LLM Wiki 内跑**——MCP/API 只把「触发」和「查询」外置，没有把「编译」外置。

### 3.4 约束与前提

| 约束 | 说明 |
|---|---|
| LLM Wiki 需保持运行 | API 是桌面应用内置的，应用关了就不可用 |
| 同机部署 | API 默认仅 `127.0.0.1`；如需异机，可设 `LLM_WIKI_BIND_HOST=0.0.0.0` 或开启 LAN 访问（**不建议**，涉密数据） |
| 单项目 | 本仓库只有一个项目 `training-qa`，`current` 即目标项目 |
| 模型/成本 | 机器人不直接调智谱；每次问答的 token 消耗与 LLM Wiki 聊天一致 |

## 4. 企业微信方案（受限，简述）

| 方式 | 能否收消息 | 限制 |
|---|---|---|
| 群机器人 Webhook | ❌ 只能发 | 单向推送，无法做问答 |
| 自建应用回调 | ⚠️ 需公网 URL | 需企业主体 + 内网/公网服务器 |
| 智能机器人 API（2026-05 新增） | ✅ 可收 @消息 | **仅限企业内部群**，外部群/个人微信不支持 |

**结论**：企业微信官方能力在当前「个人 + 外部群」场景下不可用，本项目**不优先**；若未来进入有企业微信主体的公司，可再评估（届时需把 LLM Wiki API 暴露给企业内网，或迁移到服务端部署）。

## 5. 推荐落地路线（阶段 5 拆分）

### 5.1 MVP（先跑通单聊/群聊一问一答）

1. 建飞书自建应用 + 机器人能力 + 权限 + 长连接事件（按 2.3 六步）。
2. 写 `scripts/feishu_bot.py`：`lark-oapi` 长连接收 `im.message.receive_v1` → 解析问题 → 调 LLM Wiki `/chat` → 回复 `im.message:reply`。
3. 单机本地跑通，群内 @机器人 问答成功。

### 5.2 增强（**v0.2 已实现**，2026-09-11）

`scripts/feishu_bot.py` 已在骨架上完成下列增强（均离线校验 + 本地 API 自检通过）：

| 能力 | 实现 |
|---|---|
| **来源引用** | 把 `references[].title` 拼成卡片脚注「📎 来源：…」（最多 3 条） |
| **卡片消息** | `msg_type=interactive`：蓝头卡片，正文 `lark_md`（标题自动降级为加粗）+ 分隔线 + note 脚注（来源 / 耗时） |
| **进度反馈** | 先回「🔍 正在查询…」灰卡 → 答案就绪后 **原地 `patch` 更新**同一张卡（失败则退回新消息回复，不会丢答案） |
| **多轮上下文** | 复用 LLM Wiki `/chat` **原生 session**：请求带 `persistSession:true`，回传响应里的 `sessionId`；按 `chat_id` 维护会话、TTL 1h 自动过期。**不需要自己拼上下文** |
| **超时重试** | 超时/网络错误按 2s、4s 退避重试（默认 2 次）；HTTP 4xx/5xx 属确定性错误不重试 |
| **@识别** | 群聊剥离 `<at ...>…</at>` 提及标记；群聊仅在 @机器人 时才收到事件 |
| **内置命令** | `/help`（帮助）、`/reset`（新对话，清空上下文） |

**关键接口契约（实读 v0.6.11 源码 `mcp-server/dist/src/api-client.js`）**：

```
POST /api/v1/projects/{pid}/chat
body: { message, sessionId?, persistSession?, mode?, topK?, tools:{wiki,web,anytxt} }
resp: { projectId, sessionId, mode, message:{role,content}, references[], usage }
```

> 多轮 = 首次不传 `sessionId`，之后把上次响应里的 `sessionId` 回传即可。

**新增运维开关**（`scripts/.env`，缺省即默认值）：
`BOT_WIKI_TIMEOUT=240` / `BOT_WIKI_RETRIES=2` / `BOT_SESSION_TTL=3600` / `BOT_CARD_MAX_CHARS=4500`。

**自检与单测**（不开飞书也能验证链路）：

```bash
python scripts/feishu_bot.py --selftest   # 凭据 / 本地 API / 项目解析
python scripts/feishu_bot.py --ask "什么是短溢装"   # 直接跑一条问答链路
```
