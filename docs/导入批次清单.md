**不用为「上下文 200k」担心**——LLM Wiki 是逐份/分块处理，不是把 121 份一次性塞进上下文。真正要盯的是**速率限制（免费版并发低）**和**抽取质量**，所以用「分批导入 + 先试点」来应对。

- 语料总量：**121 份 / 约 105.2 万字符**（v0.1 为 64 份 / 约 23.7 万字符；v0.2 为 78 份 / 约 29.2 万字符）

- 模型用 **glm-4.6**（付费但便宜、质量稳、实测通过；免费 flash 模型限流严格，见下方实测结论）

## 4. 模型实测结论（2026-09-09 已实测）

| 模型 | 实测结果 |
|---|---|
| `glm-4.6` | ✅ 正常（主力推荐，付费但便宜） |
| `glm-4-flash` | ✅ 可用（轻量，质量一般） |
| `glm-5.3-flash` | ✅ 可用（轻量） |
| `glm-4.7-flash` | ⚠️ 触发**速率限制**（code 1302，免费账号并发≈1，串行导入会频繁报错） |

> 结论：**用 `glm-4.6`**，别用免费 flash——导入 64 份文档要连续大量调用，免费限流会卡死。编译成本（约 23.7 万字符 × 两步思维链 ≈ 几十万 token）用 glm-4.6 也就几块钱，值。

| 风险 | 应对 |
|---|---|
| 免费模型限流（实测 1302） | 已弃用免费模型，改 glm-4.6 |
| 抽取质量 | 先导 batch1 试点，看 wiki 页面结构是否合理 |
| 单批过大导致一次请求超限 | 每批最大 7.4 万字符，远低于 200k，无此风险 |

## 7. 截图 OCR（2026-09-11 已执行）

### 7.1 实际规模远大于预期

原以为只有 61 张独立截图（`订单培训文档/陈源浩笔记/汇报/pdf_images/manual/`），实际盘点发现还有**大量图片内嵌在 docx 里**（培训手册、智能纪要的配图），全量扫描后共 **566 张**：

| 来源 | 张数 | 说明 |
|---|---|---|
| 独立截图文件 | 67 | `pdf_images/manual/` 等目录，多为**同一页切成的碎片** |
| docx 内嵌图片 | 499 | 培训手册 / 智能纪要正文里插的 UI 截图 |

### 7.2 关键设计：按页聚合，避免碎片污染

独立截图存在 `p05_X121.png` 这类**同页切片**。若逐张 OCR，同一屏 UI 会被切成 N 段零碎文字，反而稀释知识密度。故按 `p05` 聚合为**一页一文件**，最终 67 张 → 24 个页级文件。docx 内嵌图则按「所属手册」聚合，19 份手册 → 19 个 OCR 文件。

**产出（已并入 `data/clean/`，参与脱敏与入库）**：

| 产出 | 文件数 | 字符量 |
|---|---|---|
| 独立截图 OCR | 24 | ~9.0 万 |
| docx 内嵌图 OCR | 19 | ~67.0 万 |
| 合计 | **43** | **~76.0 万** |

### 7.3 技术路线（**全程在外部完成，LLM Wiki 未参与**）

```
本地 Python 脚本 ──urllib+base64──▶ 智谱 GLM-4V API ──▶ data/ocr_cache/ ──▶ data/clean/*_截图OCR.txt
   (ocr_images.py / ocr_docx_media.py)         (断点续跑缓存)         (再进脱敏，再入 LLM Wiki)
```

| 脚本 | 依赖 | 说明 |
|---|---|---|
| `scripts/ocr_images.py` | 零依赖 | OCR 独立截图；按页聚合；`--limit/--model/--force/--workers`；结果缓存 `data/ocr_cache/` |
| `scripts/ocr_docx_media.py` | 零依赖 | 抽取 docx 内嵌图（md5 去重、过滤 <20KB 图标）→ 共用 `call_vlm` OCR → 按手册聚合；`--extract-only` 可单独抽图 |

**关键约束（已在脱敏层解决）**：截图脱敏面远大于文本——含客户实体名、银行账号/SWIFT 码、抬头地址、内网 IP、登录用户名。已在 `clean_text.py` 扩了一套截图专用结构化规则（银行账号、SWIFT、裸域名、英文/中文企业主体），OCR 文本与正文走**同一套脱敏**，故入库前已清干净。

## 10. 中断后如何「续跑」（不清库、不重做）

编译中途要停下或想继续时，**不要重跑 `reingest.py`**（它会清空 wiki、重做全部文件）。正确做法是**外科手术式续跑**：

**为什么普通 rescan 没用**：`file-snapshot` 没变时，`POST /sources/rescan` 返回 `changedTasks: []`，队列不会重建。

**做法**（只动 `file-snapshot` + `ingest-queue`，不碰 `ingest-cache`）——已固化为 `scripts/resume_ingest.py`：

```bash
# 0) 完全退出 LLM Wiki（配置/状态只在启动时读取，运行中改会被退出时回写覆盖）
python scripts/resume_ingest.py --plan     # 只读：打印「已编译 / 待续跑 / 待摘除」三组数字
python scripts/resume_ingest.py --apply    # 备份 3 个状态文件 → 摘除未编译条目 → 清空队列
# 1) 重新打开 LLM Wiki —— 应用启动时会【自动重扫】，按 diff 重建队列（见下方实测）
python scripts/resume_ingest.py --rescan   # 可选兜底：若重开后队列没重建，再手动触发
python scripts/wiki_status.py              # 自检：health + 进度 + 当前入库模型
```

> **实测确认（2026-09-11 20:32）**：手术摘掉 103 条后重开应用，**队列被自动重建为
> `1 processing + 102 pending = 103`**，无需手动 `--rescan`。这反证了 rescan 就是
> 「按 `file-snapshot` 做 diff」——所以 `--rescan` 现在只是兜底手段。

原理三步：

1. `done = ingest-cache.json["entries"]` 的 key 集合（key 是文件名 basename）= 已编译
2. `待续跑 U = raw/sources 磁盘文件 − done`；从 `file-snapshot.json["files"]` 摘掉所有 `raw/sources/*` 中 basename **属于 U** 的条目（`done` 的 16 条保留，wiki 页保留）
3. 清空 `ingest-queue.json` → `[]`，再 `POST /api/v1/projects/current/sources/rescan`；应用把 U 当「新文件」重新排队，已编译的不会重做

> 复验命令：`resume_ingest.py --plan` 应显示「snapshot raw 条目 = 已编译数、待摘除 = 0」。

**实测记录（2026-09-11）**：全量重导跑到 16/119 中断后，执行本次续跑——
`--plan` 报「磁盘 119 / 已编译 16 / 待续跑 103 / snapshot raw 119 / 待摘除 103 / 保留 16」；
`--apply` 备份到 `.llm-wiki/_resume_bak_20260911_201330/`，摘除 103 条、清空队列；
复验 `--plan` 显示「snapshot raw 条目 = 16、待摘除 = 0」，队列 `[]` 确认干净。

**停下的做法**：应用没有对外停止接口（`ingest/cancel`、`queue/clear` 等全 404）。有效办法是清空 `ingest-queue.json` → `[]`；在跑的那一份会跑完才停。要硬停则退出应用。

**为什么必须做手术（踩坑实录）**：全量重导时 `reingest.py` 把 snapshot 清空 → 119 份一次性全排队；跑完 16 份后 snapshot 里 **119 份全都在**（含那 103 份没编译的）。此时直接 rescan 会判定「无变化」→ `changedTasks: []` → **不排队 → worker 空转、编译永久卡死**。这正是「看起来队列里还有 105 pending、但怎么等都不动」的根因。

> `file-snapshot.json` 结构：`{version, updatedAt, files: {"raw/sources/x.txt": {hash,size,mtimeMs}, ...}}`。rescan 会**从磁盘重读**它，所以编辑它可精确控制「哪些文件算新增」。
