# 智能问答助手 · 项目计划书

> 一个面向简历的 LLM Agent 实战项目
> 版本 v0.4 ｜ 更新：2026-09-10 ｜ 当前阶段：阶段 2（知识库搭建，编译中）

## 一、项目概述

**一句话定位**：基于企业私有知识库的智能问答助手，让培训期新人「一句话检索到散落各处的培训知识 + 引用溯源」。

**背景与痛点**：实习培训期，培训知识散落在聊天记录、会议纪要、群文档、在线文档等多处，查找细节极其困难，新人学习成本高、重复提问多。

**核心价值**：把「人肉翻聊天记录」变成「秒级问答」，并沉淀为一个可写进简历、可讲出深度的 Agent 项目。

**技术栈**：
- 知识底座：LLM Wiki
- 工作流编排：Dify
- 问答能力：Agent（RAG）
- 落地形态：飞书 / 企业微信聊天机器人

> 注：原平台（飞书等）已停用，数据已提前下载到本地，故数据接入采用「本地文件导入」，无需平台 API。

## 二、目标与成功指标（写进简历的数字）

| 指标 | 说明 | 目标 |
|---|---|---|
| 数据覆盖 | 接入的知识源数量、消息/文档条数 | 待盘点 |
| 检索命中率 | 正确答案出现在 Top-K 召回中的比例 | ≥ 85% |
| 答案准确率 | 评测集上的端到端准确率 | ≥ 80% |
| 幻觉率 | 编造/无依据回答占比 | ≤ 5% |
| 检索效率 | 提问到出答案的平均耗时 | < 3s |
| 节省时长 | 新人找资料平均耗时下降幅度 | 待测量 |

## 三、技术架构

分层：
1. **数据层**：本地文件（已清洗脱敏的 64 份语料，按主题分 5 批）
2. **知识库层**：LLM Wiki（编译式，增量构建结构化 Wiki：实体页 + 概念页 + 来源摘要 + 知识图谱）
3. **检索层**：LLM Wiki 内置检索管线（分词搜索 + 可选向量语义搜索 LanceDB + 图谱扩展）
4. **问答/编排层**：LLM Wiki 内置 Agent（工具化：wiki/资料源/图谱检索 + 引用溯源）；（可选）Dify 作为外部编排补充，用于复杂多系统场景
5. **应用层**：飞书 / 企业微信聊天机器人（通过 LLM Wiki 本地 HTTP API `127.0.0.1:19828` 或自带 MCP server 接入）

数据流：用户提问 → LLM Wiki 内置 Agent → 多阶段检索（分词 / 向量 / 图谱）→ 带引用生成 → 溯源返回。

> 架构澄清（2026-09-10 更新）：LLM Wiki 不只是「存储/检索」组件——它**自身就内置了检索管线 + 聊天 Agent**（带 [[双链]] 溯源、思维链展示、引用面板）。因此 Dify 从「必需编排层」降级为**可选**：只有当需要跨多个外部系统做复杂编排时才引入。阶段 3/4 的核心从「搭 Dify + 搭 Agent」变成「验证并调优 LLM Wiki 的内置检索与 Agent」。

## 四、分阶段计划

### 阶段 0 · 需求分析与数据盘点（进行中）
- **目标**：摸清现状，把「模糊想法」变成「可执行需求」，并清点数据家底。
- **任务**：明确知识领域与用户画像（已完成）；确定 LLM 选型（已完成）；清点本地数据文件。
- **产出**：`docs/需求分析.md`（已完成）、数据盘点表（待办）
- **验收**：能回答「做什么、给谁做、数据在哪、用什么模型」，并有一份数据清单。

### 阶段 1 · 本地数据整理与清洗
- **目标**：把本地散落数据统一格式、清洗、规范化、脱敏。
- **任务**：清点并归类文件（文档/聊天导出/会议转写）；格式统一（转成可解析文本）；清洗（去重/去噪声）；打元数据（来源、时间、角色、主题）；脱敏（隐去人名与内部敏感信息）。
- **产出**：`data/clean/` 清洗后语料 + 数据盘点表
- **验收**：数据可检索、可溯源、无重复噪声，且已脱敏。

### 阶段 2 · 知识库搭建（LLM Wiki）
- **目标**：搭建知识底座，完成分块与向量化。
- **任务**：LLM Wiki 环境搭建与文档导入；分块策略设计（主题/时间/角色）；向量化与索引构建。
- **产出**：可用知识库 + 分块策略说明
- **验收**：能通过检索返回相关片段。

### 阶段 3 · 检索验证与调优（LLM Wiki 内置检索）
- **目标**：验证并调优 LLM Wiki 的内置检索管线，让 Top-K 命中达标。
- **任务**：用 `eval/评测集.md` 逐条提问，验证分词检索命中率；开启向量语义搜索（LanceDB，可选）对比召回提升（官方基准 58%→71%）；调分块/上下文窗口参数。
- **产出**：检索评测报告 + 调优后的检索配置
- **验收**：评测集命中率 ≥ 85%，回答带来源引用。

### 阶段 4 · Agent 问答能力
- **目标**：验证 LLM Wiki 内置 Agent 的多轮、澄清、溯源能力，必要时做增强。
- **任务**：验证内置聊天 Agent 的多轮对话与追问澄清；测试 [[双链]] 引用溯源；如需要，通过内置 Agent Skills（SKILL.md）扩展能力；（可选）用 function calling 做意图路由补充。
- **产出**：Agent 能力验证记录 + 补充的 Agent Skill
- **验收**：能处理多轮、能溯源、能限权（视需求）。

### 阶段 5 · 飞书/企微机器人接入
- **目标**：落地到真实聊天工具。
- **任务**：机器人开发与接入；通过 LLM Wiki 本地 HTTP API（`127.0.0.1:19828`）或自带 **MCP server**（`llm-wiki-mcp`）接外部系统；消息收发、卡片、群内 @ 触发。
- **产出**：可用机器人
- **验收**：在群聊里能直接问答。

### 阶段 6 · 评测与优化
- **目标**：用数据证明「做得好」。
- **任务**：构建评测集（真实问题 + 标准答案）；评测命中率/准确率/幻觉率；A/B 与迭代优化。
- **产出**：`eval/` 评测集 + 评测报告
- **验收**：三项指标达标。

### 阶段 7 · 上线与量化复盘
- **目标**：沉淀可写进简历的成果。
- **任务**：收集真实用量数据（提问数、节省时长）；复盘总结与量化成果；整理简历 bullet 与面试问答。
- **产出**：`docs/复盘报告.md` + 本地专用简历素材（不进入 GitHub 发布版）
- **验收**：能拿出一份有数字的项目总结。

## 五、技术选型

| 环节 | 候选 | 备注 |
|---|---|---|
| 知识底座 | LLM Wiki | 已定（v0.6.11 便携版，编译式） |
| 工作流 | LLM Wiki 内置 Agent 为主；Dify 可选 | Dify 仅在多系统复杂编排时才引入 |
| 大模型 | 智谱 GLM（glm-4.6 主力） | 已定，OpenAI 兼容接入，实测通过 |
| 向量库 | LanceDB（LLM Wiki 内置） | 可选，阶段 3 开启对比召回 |
| 对外接入 | LLM Wiki HTTP API / 自带 MCP server | 阶段 5 接机器人 |
| 机器人 | 飞书 / 企业微信 | 阶段 5 确认 |

## 六、风险与应对

| 风险 | 应对 |
|---|---|
| 真实数据涉密 | 本地资料先脱敏（隐去人名/内部敏感信息）再用于 demo 与简历 |
| 数据规模/格式未知 | 先盘点，不足则补充模拟数据并注明来源 |
| 大模型 API 成本/合规 | 优先国产模型，控制 token |
| 检索效果不达标 | 混合检索 + 重排 + 分块调优 |
| 时间有限 | 先跑通 MVP（阶段 0→5），再补评测 |

## 七、简历价值点（目标写法）

- 主导搭建基于 LLM + RAG 的企业知识问答助手，覆盖 N 类知识源、M 条数据。
- 设计多源非结构化数据的清洗与分块方案，检索命中率提升至 X%。
- 用 Dify 编排混合检索 + 重排 + 意图路由工作流，幻觉率控制在 X% 以内。
- 接入飞书/企业微信机器人，服务 N 名用户，新人找资料耗时下降 X%。
