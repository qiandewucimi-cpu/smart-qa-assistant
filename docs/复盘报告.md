## 4. 关键决策复盘（哪些判断是对的）

### 4.1 把脱敏做成「入库前唯一闸门 + 入库后巡检」

实测发现 LLM 编译会把客户名**扩散成独立实体页与索引**，事后清理需改动 24+ 个 wiki 页并重建索引。
因此定为「先脱敏再入库」，再用 `audit_leaks.py` 入库后反查兜底（双保险）。
**代价**：词表是打地鼠，必须持续维护；**收益**：公开仓库与简历零合规风险。

### 4.2 命中率不达标时，先怀疑工具链而不是模型（本轮最值钱的一条）

v0.2 的 81.0% 里有 **2 分是被评测脚本自身吃掉的**：

| 缺陷 | 症状（易误判） | 修复 |
|---|---|---|
| 脚本走 `/projects/current/chat`，`currentProject` 为 null 时该端点 **404** | 全题失败，**看起来像网关挂了** | 新增 `resolve_project_id()`，从 `/api/v1/projects` 取 ID |
| 网关 502 抖动**无重试**，直接判失败 | 偶发、不可复现的"模型答不出" | 对 429/5xx/超时加指数退避重试（3 次） |
| 顶层 `references` 有时为空，无法区分「检索到未采用」与「真零召回」 | 把**检索抖动**误判成**语料缺口** | 从 `events` 兜底提取引用 |

修掉后 O3、O5、C1 三题转命中，**+4.7pp**。

### 4.3 瓶颈转移判断：从「语料覆盖」到「检索稳定性与排序」

三轮归因后发现：剩余 3 道未命中里 **0 道是语料缺失**——2 道是检索偶发零召回（内容在库、上轮还命中过），
1 道是检索排序。**据此停止扩充语料**，把精力转向开向量检索，避免无效的数据堆砌。
这个「判断的转移」本身就是结论。

### 4.4 分模型路由（入库用快、问答用强）

自建 `bench_models.py` 实测定位编译瓶颈：glm-4.7 单次 **66.6s**（九成输出是思维链）
vs glm-4.5-air **7.1s**（**快 9.4×**）。落地「入库 `glm-4.5-air`、问答 `glm-4.7`、
截图 OCR `glm-4v-flash`」的分路由，全量编译耗时从数十小时降到可接受范围。

### 4.5 指标一律带样本量与置信界（避免被自己的数字击穿）

放弃「幻觉率 0%」这类表述，改为「**0/21（95% 置信上界 13.3%）**」。
0 事件的 Clopper–Pearson 单侧上界 `1-α^(1/n)` 让口径可被追问、可被验证——**敢认局限比数字漂亮更可信**。

### 4.6 主动补测「拒答准确性」，补齐零幻觉的评估盲区

22 题主评测的「幻觉 0」有**结构性盲区**：那 21 题的答案语料里全都有，模型只要正常检索就能答对，
**没机会暴露「没有依据时会不会硬编」**。故补 13 题专项（**一正一反，缺一不可**）：

| 组别 | 题数 | 期望行为 | 实测 |
|---|---|---|---|
| X 类·语料外（含 2 道「相邻概念诱导」题） | 8 | 拒答 | **8/8 正确拒答、0 编造** |
| N 类·语料内冷门对照（22 题未问过的模块） | 5 | 作答 | **5/5 正常作答、0 误拒** |

只测 X 类是不够的——若模型「检索不到就一律拒答」，光看 X 类会得出「拒答能力很强」的**错误结论**；
加对照组才能区分**真拒答** vs **摆烂式拒答**。

> **最有价值的发现：模型是「内容驱动」而非「检索驱动」。** X 类 8 题里有 7 题检索都返回了 5~15 条内容，
> 模型仍正确拒答。这**避开了 RAG 最常见的失败模式——检索恒有返回 → 模型强行凑答案**。

## 6. 用户价值度量（阶段 7 的核心待办）

### 6.1 现状：当前**没有**真实用量数据

机器人已在真实群聊可用，但**此前没有任何埋点**，因此「找资料耗时下降多少」「服务了多少人」
这两个指标**目前无数据支撑**。

> **本报告不编造这两个数字。** 计划书 §二 的「节省时长」列为「待测量」，此处如实维持「待实测」。

### 6.2 已落地：用量埋点 + 统计脚本（本次新增）

为让这两个指标**可被真实测量**，本次补上了采集链路：

- `scripts/feishu_bot.py` 新增用量埋点：每次问答追加一行 JSON 到 `data/usage_log.jsonl`
  （`data/` 已被 `.gitignore` 隔离，不入公开仓库）。
- **只记元数据，不记问题原文**——业务提问可能自带客户名/订单号等敏感信息，
  与项目「脱敏后才落盘」的口径保持一致；问题与会话均以**单向哈希**记录，可统计去重与频次，无法还原内容。
- 记录字段：时间戳、会话哈希、问题哈希与长度、**耗时**、**引用来源数**、
  是否**多轮追问**、是否**拒答标记**、成功/失败。
- `scripts/usage_stats.py` 一键出数：
  ```
  python scripts/usage_stats.py            # 飞书群聊真实用量
  python scripts/usage_stats.py --md       # 额外输出 Markdown 表（贴回本报告用）
  ```
  输出：总提问数 / 成功率 / **去重提问数** / **唯一会话数（人数近似）** /
  延迟 P50·P90·均值 / 平均来源数 / 拒答标记率 / 多轮追问占比 / 按天分布。

### 6.3 推荐测量方案（「找资料耗时」对照实验）

| 步骤 | 做法 |
|---|---|
| 1. 选样 | 选 5~10 个**典型业务问题**（覆盖概念/流程/操作），问题不预先给答案 |
| 2. 人工基线 | 让培训期新人用既有方式（翻聊天记录 / 群文档 / 手册）找全答案，记录**平均耗时（分钟）** |
| 3. 机器侧 | 同一批问题问机器人，读埋点里的**延迟字段**（秒） |
| 4. 出数 | 效率提升倍数 = 人工平均耗时 ÷ 机器平均耗时；同时报告**一次答准率**与**是否需追问** |
| 5. 口径 | 说明「人工耗时为基线组小样本（n≤10），非全量统计」；不把 61.5s 的机器延迟包装成"秒级"优势 |

> ⚠️ **诚实提醒**：当前机器人延迟 P50 61.5s，**它的价值不在"快"，而在"能一次拿到带出处的完整答案"**。
> 人工翻找虽慢，但单次成本高且**答案无法溯源**——真正的价值差是
> **「10~30 分钟且可能找不齐」→「1 分钟且每条结论可点回来源页」**，
> 而非「秒级」。对外表述务必按这个口径，否则会被 61.5s 反杀。

| 指标 | 状态 |
|---|---|

## 8. 方法论沉淀（可迁移到其他项目）

1. **先排除工具链问题，再谈模型优化。** 指标不达标时，第一反应应是「是不是我的测试/管线错了」。
   本项目 4.7pp 的提升全部来自修评测脚本，而非调模型或加数据。
2. **「0 缺陷 / 100%」类指标必须带样本量与置信界。** 0/N 的 95% 上界 = `1-0.05^(1/N)`；
   N=21 → 13.3%，要到「<5%」需 N≥60。单写百分比在评审/面试中必然被击穿。
3. **评估盲区要用「一正一反」对照补齐。** 想证明「不会就拒答」，必须同时有
   「语料外应拒答」与「语料内应作答」两组，否则无法区分**真拒答**与**摆烂式拒答**。
4. **脱敏是持续动作，不是一次性任务。** 只要有人改文档就可能把真实词写回注释里的"举例说明"；
   每次提交前必须**全量 + 词边界**反扫。
5. **能复算的数字才是资产。** 每个结论都对应一个可执行脚本（`corpus_stats.py` /
   `check_coverage.py` / `audit_leaks.py` / `eval_chat.py` / `usage_stats.py`），
   面试被追问时能立刻说出「哪个脚本跑出来的」，比数字本身更有说服力。
6. **判断的「转移」本身是结论。** 把瓶颈从「语料覆盖」修正为「检索稳定性」，
   直接避免了继续堆数据的无效投入——停止做错事，比多做对事更省成本。
