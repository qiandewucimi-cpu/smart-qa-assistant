# 评测报告 v1.2：框架失败「session 续跑」A/B —— 以及一个更尴尬的发现

> 日期：2026-09-12 ｜ 关联：`eval/评测报告_v1.1_知识固化与稳定性.md`、`docs/复盘报告.md` §5 坑 17

> 复算：`python scripts/ab_analysis.py`（判定规则与 Fisher 检验都在里面）
> 复跑：`python eval_chat.py --only D1,D2,P1 --repeat 5 --tag ab_cont_on`
> 　　　`python eval_chat.py --only D1,D2,P1 --repeat 5 --tag ab_cont_off --no-continue`

---

## 0. 一句话结论

**续跑这条路走通了，但它的效果没达到显著，而且它会把「没答案」换成「错答案」。**
更要命的是：这次 A/B 顺手证明了**系统自身的测量噪声（±30pp）大于我折腾过的任何一个旋钮的效应量**——
所以真正该做的不是继续调旋钮（模型 / topK / FAQ 页 / 续跑提示语），而是**扩样本 + 建基线**。

---

## 1. 这一轮是怎么找到方向的

v1.1 把「框架 8 步工具迭代上限」定为 P0，并说它「应用内置、无可配项」。后半句是查过的：
`%APPDATA%/com.llmwiki.app/app-state.json` 的全部顶层键里**没有任何 agent / 步数相关字段**。

但我此前**从没去读应用本身**。这次从应用二进制（`tools/llm-wiki/LLM Wiki.exe`）里抠出了 agent loop 的系统提示词，
两句话直接改写了问题：

```
The Agent reached the tool-iteration limit after 8 step(s). ...
Please narrow the request or ask it to continue from the latest result.
```

- 报错文案**自带逃生口**：`ask it to continue`
- 响应体里一直有 `sessionId`——而且**它早就在我自己的评测数据里**（`events[0]` 就是
  `{"session_id": "api_...", "type": "agentStart"}`，我 dump 过多次，从没看见）

**教训（已写入复盘报告坑 17）**：我前两轮一直在提「换回 glm-4.7 做对照」——那是拿**模型**这个我调得动的旋钮做文章；
而真正的线索躺在我已有的响应里。

### 1.1 可行性验证（单题，含对照）

| 调用 | 耗时 | 结果 |
|---|---|---|
| 首次提问 D1 | 58.5s | ❌ `tool-iteration limit`，无答案 |
| **带同一 `sessionId` 补一句「请直接给出最终答案」** | 22.8s | ✅ **完整正确答案**（加放系数 / 短溢装都命中） |
| 对照：不带 `sessionId`，发同一句 | 3.3s | 「抱歉，我没有收到具体的问题或上下文」 |

对照组证明答案确实来自 session 上下文，不是补的这句话本身。

### 1.2 8 步预算花在哪（D1 成功那次的 `toolEvents`）

```
 2  wiki.search   started    加放系数
 6  wiki.search   started    短溢装
10  agent.action  failed     Invalid or truncated Agent tool JSON.   ← 白扔一步
13  wiki.read_page started   wiki/concepts/加放系数.md
17  wiki.read_page started   wiki/concepts/短溢装.md
```

D1 是**对比题**，天生要查两个概念：2×search + 2×read_page，再加 JSON 格式错误白扔的 1~2 步，
就贴着 8 步上限走。这解释了它为什么长期摇摆——**不是知识缺口，是步数预算刚好不够用**。

## 2. A/B 结果（同时段双臂，D1/D2/P1 各 5 次）

单变量：只有「撞上限后是否补跑」不同（`--no-continue` 作对照臂），同模型、同 topK=15、同 FAQ 页。

| 题 | 续跑开 | 续跑关 |
|---|---|---|
| D1 | **4/5**〔hit, refuse〕 | 3/5〔hit, **raw_dump**〕 |
| D2 | 3/5〔hit, **hallucination**〕 | 3/5〔hit, **json_dump**, limit〕 |
| P1 | **5/5**〔hit〕 | 3/5〔hit, limit〕 |
| **合计** | **12/15** | **9/15** |

**Fisher 单侧 p = 0.213 → 不显著。** 不能说「续跑把命中率提上去了」。

### 2.1 但失败的性质确实变了（这才是关键）

| 臂 | 错误答案（幻觉/答偏） | 无答案（limit/直吐/JSON/拒答） |
|---|---|---|
| 续跑开 | **2** | 1 |
| 续跑关 | **0** | 6 |

续跑把 6 次「框架没给出答案」压到 1 次，代价是冒出 2 次**自信的错答案**。
典型（A 臂 D2#3）：

> 「待核单」指的是已经创建但**尚未经过审核确认**的订单……

而语料里待核单恰恰是**订单审核通过后**由系统自动生成的——**语义与语料相反**。

对一个把「0 幻觉」当卖点的项目，**这个交换未必划算**。因此默认提示语已改为防幻觉版本：

```
请基于上面已检索到的内容直接给出最终答案，不要再调用任何工具。
如果已检索到的内容不足以回答，请明确说明缺少什么，不要推测或编造。
```

### 2.2 顺手发现第三种失败模式

`json_dump`：答案直接把 agent loop 的 `{"action":"final","answer":"..."}` 原样吐出来（对照臂 D2#2）。
内容其实是对的，但用户看到的是裸 JSON。`framework_failure()` 已加入该检测。

至此已观测到 **3 种框架失败模式**：`limit` / `raw_dump` / `json_dump`。

## 3. ⚠️ 更尴尬的发现：噪声比任何旋钮的效应都大

对照臂（续跑关）这次 D1 是 **3/5**。
而 v1.1 在同一配置（同模型、同 topK、同 FAQ 页）下测的 D1 是 **1/10**。

| 时段 | 同一配置下 D1 命中率 |
|---|---|
| v1.1 A/B（09-12 下午） | 1/10 = 10% |
| v1.2 对照臂（09-12 晚） | 3/5 = 60% |

**差 50pp，什么都没改。** 这意味着：

1. v1.1 里「D1 命中率 1/10」这个数字**不能当作 D1 的能力指标**，它只是一段时间的采样；
2. **任何 n=5/题 的单变量 A/B 都分辨不出 ±30pp 以内的效应**——包括这次的续跑（+20pp，p=0.213）；
3. 我前面几轮反复归因的「topK 副作用」「换模型的代价」，**都可能只是噪声**。v1.1 已经撤回了一处，
   现在看，撤回得还不够彻底。

**结论：继续调旋钮是无效劳动。下一步必须是扩样本（≥60 题）+ 每题多次基线采样。**

## 5. 待办（按此顺序，不再调旋钮）

| 优先级 | 事项 |
|---|---|
| **P0** | 扩样本到 **≥60 题**，并对每题做 **≥5 次**基线采样，先拿到稳定的 per-question 命中率，再谈任何 A/B |

| P1 | 用「对比题合并成一页」的思路减少步数消耗（D1/D2 都是对比题，天生 2× 检索） |
| P1 | 复核后再决定是否把续跑同步进 `feishu_bot.py` |
