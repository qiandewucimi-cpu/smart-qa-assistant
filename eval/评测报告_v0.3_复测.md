## 4. 剩余问题与归因

### 4.1 C3 / O4 零召回（2 题）—— 本轮新出现的**稳定性**问题

- **不是语料缺失**：C3「短溢装」、O4「色码明细」在上一轮均命中（各 5 条引用），内容确实在库。
- **不是网关故障**：本轮 0 次 502，两题都是秒级返回且 events 里 wiki.search 结果为空。
- **结论：检索层偶发失效**。观察依据是同一份语料、同一套题目，两次运行结果不一致。

根因分析（结合配置）：
1. **`embeddingConfig.enabled = false`（向量检索关闭）** —— 检索只剩「关键词 token + 图谱」两路，
   语义相近但字面不同的提问无法召回，抗抖动能力差。
2. wiki.search 前有一个 **LLM 查询改写**步骤（events 中 `toolStart.input` 是改写后的词，
   如 C1 的 "订单理单待核单"）。改写结果随 LLM 采样波动，一旦改偏就可能零召回。

建议（按性价比排序）：
1. **开启向量检索**（配 embedding 模型）→ 补上语义召回，直接降低零召回概率；
2. 或在检索侧做**同义词/别名扩展**（如「色码明细」→「色码」「明细」「自动带入」）；
3. 评测侧加「零召回自动重试一次」—— 用工程手段先把抖动滤掉，避免误判为知识缺口。

### 4.2 P1 答偏（1 题）—— 连续两轮，属检索排序问题

答案确实在语料里（O1 的回答中就引用了「内部合同号+次款号、每个单品款号单独生成」），
但 P1 召回的 5 条里正相关性偏低，模型只概括出「数据汇总」。
属**检索排序/分块粒度**问题，非语料缺口。

### 4.3 延迟偏高 —— 与质量门槛的明确差距

| 指标 | 本轮实测 | 质量门槛目标 | 结论 |
|---|---|---|---|
| 平均耗时 | **74.1s**（剔除 D1 异常后 61.8s） | < 3s | ❌ 差距大 |
| P50 | **61.5s** | < 3s | ❌ |
| 最快 / 最慢 | 12.1s / 331.6s（含 1 次超时重试） | — | — |

说明：这是**编译式知识库 + 推理型问答模型（glm-4.7）的端到端耗时**，含查询改写、
检索、长答案生成，且本地 API 为单并发串行。与「纯向量检索 + 快模型」的 3s 目标不是同一口径，
但作为**交付指标仍需如实标注**。若要做进实时机器人场景，需换快模型或加缓存。
